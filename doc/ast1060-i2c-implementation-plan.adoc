== Project Overview

**Objective:** Integrate the AST1060 I2C driver with the Hubris I2C API framework to enable both master and slave mode operations.

**Current State:**

- ✅ Low-level AST1060 hardware driver (`drv/ast1060-i2c`)
- ✅ Generic I2C server framework (`drv/openprot-i2c-server`)
- ✅ I2C API definitions (`drv/i2c-api`, `drv/i2c-types`)
- ✅ `I2cHardware` trait with slave mode operations (`drv/i2c-types/src/traits.rs`)
- ✅ AST1060 slave mode implementation (`drv/ast1060-i2c/src/slave.rs`)
- ✅ Server driver integration (`drv/ast1060-i2c/src/server_driver.rs`)
- ✅ MCTP server using I2C slave mode (`task/mctp-server/src/main.rs`)
- ✅ Example applications (`app/ast1060-i2c-example/`, `app/ast1060-mctp-i2c-echo/`)
- ✅ Testing infrastructure (`drv/ast1060-i2c/aardvark_test.py`, `TEST-PLAN.md`)

**Remaining Work:**

- [ ] Hardware validation on physical AST1060 board
- [ ] Performance benchmarking (latency, throughput)
- [ ] Stress testing under sustained load
- [ ] Documentation review and finalization

**Success Criteria:**

1. Application tasks can use I2C master mode via standard API
2. Application tasks can receive I2C slave messages via notifications
3. Message loss rate < 0.1% under normal load
4. Latency < 25µs from hardware interrupt to client notification
5. All unit and integration tests pass

== Architecture Summary

=== Design Decisions Made

1. **Single Message Buffer:**
   - Decision: Use `Option<(u8, SlaveMessage)>` instead of queue
   - Rationale: Minimizes memory usage (~270 bytes total)
   - Trade-off: Client must retrieve promptly; overflow causes message loss
   - Mitigation: MCTP layer handles retransmission

2. **Single Subscriber Pattern:**
   - Decision: One global `notification_client: Option<(TaskId, u32)>`
   - Rationale: Simplifies implementation; typical use case is single MCTP server
   - Trade-off: Cannot have multiple independent I2C protocol consumers
   - Mitigation: Use MCTP-layer multiplexing for multiple protocols

3. **Interrupt-Driven Notifications:**
   - Decision: Use `sys_post()` for immediate notification
   - Rationale: Low latency, power efficient
   - Trade-off: Requires prompt client response
   - Benefit: µs-scale notification delivery

4. **No Controller ID in SlaveMessage:**
   - Decision: `SlaveMessage` does not include controller field
   - Rationale: Single-protocol deployments don't need it
   - Impact: MCTP deployments unaffected (use source EID at MCTP layer)
   - Future: Can extend if multi-protocol scenarios arise

== Risk Management

=== Risk 1: Hardware Availability

**Probability:** Medium
**Impact:** High
**Mitigation:**

- Use QEMU for initial development and simulation
- Mock hardware for unit tests
- Coordinate hardware access early

---

=== Risk 2: Interrupt Latency Too High

**Probability:** Low
**Impact:** Medium
**Mitigation:**

- Profile interrupt handler during hardware validation
- Optimize critical path if needed
- Current design targets < 5µs interrupt latency

---

=== Risk 3: Buffer Overflow in Production

**Probability:** Medium
**Impact:** Medium
**Mitigation:**

- Single message buffer is intentional design choice
- MCTP layer handles retransmission for dropped packets
- Monitor statistics in production
- Document tuning procedures if queue needed later

---

=== Risk 4: Hardware-Specific Issues

**Probability:** Low
**Impact:** High
**Mitigation:**

- Review AST1060 errata
- Test with multiple I2C devices
- Document any workarounds needed

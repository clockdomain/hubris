= I2C Slave Mode Support Architecture
:toc: left
:toclevels: 3
:sectnums:
:source-highlighter: rouge

== Executive Summary

I2C slave mode enables embedded systems to act as responders on an I2C bus, accepting commands from external masters. This is essential for:

- **Management Communication**: BMC/host communication via MCTP-over-I2C
- **Configuration Access**: Remote configuration and monitoring
- **Peer-to-Peer**: Device-to-device communication in multi-board systems
- **Standards Compliance**: PMBus, SMBus, IPMI protocols

This document describes the architecture for slave mode support in Hubris, independent of specific hardware implementation.

== Architecture Overview

=== Three-Layer Design

```
┌─────────────────────────────────────────────────────┐
│  APPLICATION LAYER                                  │
│  - Protocol implementation (MCTP, PMBus, etc.)      │
│  - Business logic                                   │
│  - Uses high-level API                              │
└──────────────────┬──────────────────────────────────┘
                   │ drv-i2c-api (I2cDevice methods)
                   │ - configure_slave_address()
                   │ - enable_slave_receive()
                   │ - enable_slave_notification()
                   │ - get_slave_message()
                   │ - disable_slave_notification()
                   │ - disable_slave_receive()
                   ▼
┌─────────────────────────────────────────────────────┐
│  FRAMEWORK LAYER                                    │
│  - IPC handling (openprot-i2c-server)               │
│  - Notification delivery via sys_post()             │
│  - Operation dispatch                               │
│  - Hardware abstraction (I2cHardware trait)         │
│  - Single message buffer per controller             │
└──────────────────┬──────────────────────────────────┘
                   │ Hardware trait calls (I2cHardware)
                   │ - configure_slave_mode()
                   │ - enable_slave_receive()
                   │ - disable_slave_receive()
                   │ - check_slave_data()
                   │ - read_slave_data()
                   │ - clear_slave_interrupts()
                   ▼
┌─────────────────────────────────────────────────────┐
│  HARDWARE LAYER                                     │
│  - Platform-specific driver (AST1060, STM32, etc.)  │
│  - Register manipulation                            │
│  - Interrupt handling                               │
│  - Hardware buffer management                       │
└─────────────────────────────────────────────────────┘
```

=== Key Design Principles

1. **Hardware Agnostic**: Application code works across different I2C controllers
2. **Interrupt Driven**: Low latency, power efficient notification model
3. **Single Message Buffer**: Minimizes memory usage; client must retrieve promptly
4. **Single Subscriber**: One task can receive notifications at a time
5. **Protocol Neutral**: Framework doesn't interpret message contents

== Data Types

=== SlaveMessage

```rust
/// Represents a message received while operating in I2C slave mode
pub struct SlaveMessage {
    /// The 7-bit I2C address of the master that sent this message
    pub source_address: u8,
    /// Length of the message data in bytes (0-255)
    pub data_length: u8,
    /// The message data (only first data_length bytes are valid)
    pub data: [u8; 255],
}

impl SlaveMessage {
    /// Get the valid data portion of this message
    pub fn data(&self) -> &[u8] {
        &self.data[..self.data_length as usize]
    }
}
```

=== ResponseCode (Slave-Specific)

```rust
pub enum ResponseCode {
    // ... other codes ...
    SlaveAddressInUse,          // Address already configured
    SlaveNotSupported,          // Slave mode not supported on this controller
    SlaveNotEnabled,            // Slave receive not enabled
    SlaveBufferFull,            // Buffer overflow (messages may be dropped)
    BadSlaveAddress,            // Invalid address (reserved or out of range)
    SlaveConfigurationFailed,   // Hardware configuration failed
    NoSlaveMessage,             // No message available
    NotificationFailed,         // Failed to register for notifications
}
```

=== IPC Operations

The following `Op` codes are used for slave mode IPC:

```rust
pub enum Op {
    // Master mode operations...
    WriteRead = 1,
    WriteReadBlock = 2,

    // Slave mode operations
    ConfigureSlaveAddress = 3,     // Set slave address
    EnableSlaveReceive = 4,        // Start listening for messages
    DisableSlaveReceive = 5,       // Stop listening
    EnableSlaveNotification = 6,   // Register for notifications
    DisableSlaveNotification = 7,  // Unregister notifications
    GetSlaveMessage = 8,           // Retrieve received message
}
```

== Components

=== Application Layer

**Responsibilities:**
- Implement protocol logic (MCTP, PMBus, etc.)
- Configure slave address
- React to notifications
- Retrieve and process messages
- Send responses (via master mode)

**Example Flow:**
```
1. Configure slave address (e.g., 0x1D for MCTP endpoint)
2. Enable slave receive mode
3. Register for notifications
4. Wait for notification (sys_recv_open)
5. Retrieve message (get_slave_message)
6. Process message (parse MCTP, etc.)
7. Send response if needed (write/read operations)
8. Repeat from step 4
```

**Isolation:**
- Each application task is isolated
- No direct hardware access
- Uses IPC to communicate with driver

=== Framework Layer

**Responsibilities:**
- Accept IPC requests from applications
- Validate parameters
- Dispatch to hardware abstraction layer
- Manage notification subscriptions
- Deliver notifications via kernel sys_post()
- Buffer messages between hardware and application

**Key State:**
- Global notification subscriber: `Option<(TaskId, u32)>` (one client at a time)
- Single pending message buffer: `Option<(u8, SlaveMessage)>` (controller_id, message)
- Slave configuration per controller

NOTE: The current implementation uses a single message buffer rather than a queue.
This minimizes memory usage but requires clients to retrieve messages promptly
before the next interrupt overwrites the buffer.

**Notification Flow:**
```
Hardware IRQ → Driver Task → sys_post(client_task, mask) → Client Task
```

**Why Indirect?**
- Kernel doesn't deliver hardware interrupts directly to applications
- Driver task acts as trusted intermediary
- Maintains memory isolation between tasks
- Allows buffering and error handling

=== Hardware Layer

**Responsibilities:**
- Configure I2C controller registers
- Handle hardware interrupts
- Read from hardware buffers/FIFOs
- Copy to software buffers
- Provide uniform interface via I2cHardware trait

**Hardware Diversity:**
Different I2C controllers have varying FIFO sizes, queuing capabilities, and
controller counts. See link:i2c-openprot-architecture.adoc#_hardware_diversity[Hardware Diversity]
in the openprot architecture document for a detailed comparison.

**AST1060 Specifics:**
The AST1060 uses a 32-byte hardware packet buffer (not a FIFO). Each received
packet must be read before the next packet arrives. This hardware constraint
drove the single `SlaveMessage` buffer design - clients must retrieve messages
promptly via `get_slave_message()` before the next interrupt overwrites the buffer.

**Abstraction Goal:** Hide hardware differences from upper layers

[[mpu-region-budget]]
=== MPU Region Budget per Task

ARMv7-M provides 8 MPU regions, with 1 region reserved for the kernel,
leaving 7 usable regions per task.

**Regions Required per I2C Controller:**

|===
| Resource | Regions | Purpose

| scu
| 1
| Clock/reset/pinmux (shared)

| i2c_global
| 1
| Timing configuration (shared)

| i2cN
| 1
| Controller registers (0x80 bytes)

| i2c_bufferN
| 1
| Buffer registers (0x20 bytes)
|===

**Practical Limits:**

- 1 controller: 4 regions → Works, 3 regions spare
- 2 controllers: 6 regions → Works, 1 region spare
- 3+ controllers: 8+ regions → **Impossible**

**Why Not a Single Large Region?**

The I2C address space (0x7e7b0000-0x7e7b0dff) is ~3.5KB, but:

- ARMv7-M MPU requires power-of-two aligned regions
- Controllers (0x80 bytes) and buffers (0x20 bytes) don't align well
- Would need 4KB region covering unused memory = security risk

**Implication:** Systems requiring more than 2 I2C controllers in slave mode
must deploy multiple `openprot-i2c-server` task instances, each handling
at most 2 controllers.

== Message Flow

=== Interrupt-Driven Receive Flow

```
┌─────────────┐
│ I2C Master  │
│ (External)  │
└──────┬──────┘
       │ I2C Write Transaction
       │ Address: 0x1D, Data: [0x0F, 0x01, ...]
       ▼
┌──────────────────────────────────────────┐
│ I2C Hardware                             │
│ - Address matches configured 0x1D        │
│ - Receives data into hardware buffer    │
│ - Generates interrupt                    │
└──────┬───────────────────────────────────┘
       │ Hardware Interrupt
       ▼
┌──────────────────────────────────────────┐
│ Kernel                                   │
│ - Dispatches interrupt to driver task   │
└──────┬───────────────────────────────────┘
       │ Task Notification
       ▼
┌──────────────────────────────────────────┐
│ I2C Driver Task (Interrupt Handler)     │
│                                          │
│ 1. Read hardware status                 │
│ 2. Copy data from hardware buffer       │
│ 3. Create SlaveMessage struct           │
│ 4. Push to software ring buffer         │
│ 5. sys_post(client_task_id, notif_mask) │
│                                          │
│ ⏱ Target: < 5µs for AST1060             │
└──────┬───────────────────────────────────┘
       │ Kernel Notification (sys_post)
       ▼
┌──────────────────────────────────────────┐
│ Kernel                                   │
│ - Unblocks client task                  │
│ - Sets notification bit                 │
└──────┬───────────────────────────────────┘
       │ Task Wakeup
       ▼
┌──────────────────────────────────────────┐
│ Client Application Task                  │
│ - sys_recv_open() returns               │
│ - Check sender == KERNEL                │
│ - Check notification bit                │
│ - Call get_slave_message()              │
└──────┬───────────────────────────────────┘
       │ IPC Request (get_slave_message)
       ▼
┌──────────────────────────────────────────┐
│ I2C Driver Task (IPC Handler)           │
│                                          │
│ 1. Pop message from ring buffer         │
│ 2. Copy to IPC lease                    │
│ 3. Reply to client                      │
└──────┬───────────────────────────────────┘
       │ IPC Reply
       ▼
┌──────────────────────────────────────────┐
│ Client Application Task                  │
│ - Receives SlaveMessage                 │
│ - Processes protocol (MCTP, etc.)       │
│ - May send response via master mode     │
└──────────────────────────────────────────┘
```

**Sequence:**

1. Master starts write to slave address
2. Transaction completes (e.g., 32 bytes @ 400kHz takes ~640µs)
3. Hardware interrupt fires
4. Kernel dispatches to driver task
5. Driver reads hardware buffer
6. Driver stores message in `pending_slave_msg`
7. Driver calls `sys_post()` to notify client
8. Kernel unblocks client task
9. Client calls `get_slave_message()`
10. Client receives and processes message

== Buffering Strategy

=== Current Implementation: Single Message Buffer

The current implementation uses a **single message buffer** per driver instance:

```rust
// In openprot-i2c-server
let mut pending_slave_msg: Option<(u8, SlaveMessage)> = None;
let mut notification_client: Option<(TaskId, u32)> = None;
```

**Design Rationale:**
- Minimizes memory usage on resource-constrained platforms
- Matches the interrupt-driven model where each interrupt corresponds to one message
- Simplifies implementation and reduces stack usage
- Client must retrieve messages promptly before next interrupt

**Message Flow:**

Actors:

- **Master**: External I2C master device (e.g., BMC, host processor) - outside Hubris
- **Hardware**: I2C controller peripheral (e.g., AST1060 I2C2) - generates interrupts
- **Driver**: `openprot-i2c-server` task running in Hubris - handles interrupts, buffers messages
- **Client**: Application task (e.g., MCTP server) running in Hubris - processes messages

```
Time →

Master         Hardware       Driver                 Client
(external)     (I2C periph)   (i2c server)           (app task)
  |              |              |                      |
  | Write[Msg1]  |              |                      |
  |------------->| IRQ          |                      |
  |              |------------->| read_slave_data()    |
  |              |              | Store Msg1           |
  |              |              | sys_post()           |
  |              |              |--------------------->|
  |              |              |                      | (wakes up)
  |              |              |<---------------------|get_slave_message()
  |              |              |--------------------->| Returns Msg1
  |              |              |                      | (processing Msg1)
  | Write[Msg2]  |              |                      |
  |------------->| IRQ          |                      |
  |              |------------->| read_slave_data()    |
  |              |              | Store Msg2           |
  |              |              | sys_post()           |
  |              |              |--------------------->|
```

**Important Constraint:**
If a second message arrives before the client retrieves the first, the first
message will be overwritten. Protocols like MCTP handle this at higher layers
with sequence numbers and retransmission.

=== Overflow Handling

**Current Implementation:**
When a new message arrives and one is already pending, the new message
overwrites the old one. The client receives `ResponseCode::NoSlaveMessage`
if they call `get_slave_message()` after the message has been overwritten.

**Protocol-Level Mitigation:**
- MCTP uses sequence numbers to detect missing packets
- SMBus uses PEC (Packet Error Checking) for integrity
- Higher-layer protocols handle retransmission

== Notification Model

=== Single Subscriber Pattern

**Design Decision:** One task per driver instance can subscribe to slave notifications

Each `openprot-i2c-server` instance has its own `notification_client: Option<(TaskId, u32)>`.
This means only one task can receive slave mode notifications from a given driver instance.

**Rationale:**
1. **Simplicity**: Single `Option<(TaskId, u32)>` per driver minimizes state
2. **Clear Ownership**: One task owns slave traffic for that driver instance
3. **Typical Usage**: Most systems have a single protocol handler (e.g., MCTP server) per bus

**Architecture (Per Driver Instance):**
```
┌──────────────────────────────────────────────────┐
│ Driver Instance A (I2C0, I2C1)                   │
│   I2C0 ─┬──→ notification_client (one task)      │
│   I2C1 ─┘                                        │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│ Driver Instance B (I2C2, I2C3)                   │
│   I2C2 ─┬──→ notification_client (one task)      │
│   I2C3 ─┘                                        │
└──────────────────────────────────────────────────┘
```

NOTE: Due to MPU region constraints, each driver task can manage at most 2 I2C
controllers. Systems requiring more controllers must deploy multiple driver
instances. See <<mpu-region-budget>> for details.

**Limitation: No Controller Identification**

The `SlaveMessage` struct does not include a controller ID field. When messages arrive,
the client cannot determine which I2C controller received the message.

**Impact for MCTP-based deployments:** This limitation is **not a concern** for typical
MCTP deployments. Source identification occurs at the MCTP layer via the source EID
field in the MCTP header. Whether using SPDM, PLDM, or vendor-defined messages, the
MCTP stack properly tracks message sources through the protocol's own addressing.

**Impact for non-MCTP scenarios:** If multiple I2C controllers were configured for
different non-MCTP protocols simultaneously, the lack of controller ID would prevent
protocol disambiguation. Such scenarios would require extending `SlaveMessage` to
include the controller ID, or using separate I2C driver instances per protocol.

== Protocol Integration

=== MCTP-over-I2C

MCTP (Management Component Transport Protocol) is the primary use case for I2C slave mode
in Hubris RoT deployments. MCTP provides a transport layer for security and management
protocols including SPDM, PLDM, and vendor-defined messages.

For detailed MCTP-I2C integration documentation, see:
link:mctp-i2c-integration.adoc[MCTP-over-I2C Integration]

**Key Points:**

- MCTP uses EID (Endpoint ID) for routing, not I2C addresses
- Single subscriber pattern works well since MCTP server handles demultiplexing
- Message type field routes to SPDM (0x05), PLDM (0x01), or vendor messages
- The `SlaveMessage` controller ID limitation does not affect MCTP deployments

=== PMBus/SMBus

**Power Management Bus**

```rust
use drv_i2c_api::*;
use userlib::*;

// PMBus device address
const PMBUS_ADDR: u8 = 0x40;
const PMBUS_NOTIF: u32 = 0x0001;

let device = I2cDevice::new(
    i2c_task,
    Controller::I2C1,
    PortIndex(0),
    None,
    PMBUS_ADDR,
);

device.configure_slave_address(PMBUS_ADDR)?;
device.enable_slave_receive()?;
device.enable_slave_notification(PMBUS_NOTIF)?;

let mut msg_buf = [0u8; 256];
loop {
    let msg = sys_recv_open(&mut msg_buf, PMBUS_NOTIF);

    if msg.sender == TaskId::KERNEL && (msg.operation & PMBUS_NOTIF) != 0 {
        match device.get_slave_message() {
            Ok(slave_msg) => {
                let cmd = slave_msg.data()[0]; // First byte is command

                match cmd {
                    PMBUS_READ_VOUT => send_voltage_reading(),
                    PMBUS_READ_IOUT => send_current_reading(),
                    PMBUS_READ_TEMPERATURE => send_temperature(),
                    _ => {} // Unsupported command
                }
            }
            Err(ResponseCode::NoSlaveMessage) => {}
            Err(_) => {}
        }
    }
}
```

**Key Requirements:**
- Command/data protocol
- Block read/write support
- PEC (Packet Error Checking)
- Alert response address

=== Custom Protocols

**General Pattern:**
```rust
use drv_i2c_api::*;
use userlib::*;

const CUSTOM_ADDR: u8 = 0x55;
const RX_NOTIF: u32 = 0x0001;

let device = I2cDevice::new(
    i2c_task,
    Controller::I2C1,
    PortIndex(0),
    None,
    CUSTOM_ADDR,
);

device.configure_slave_address(CUSTOM_ADDR)?;
device.enable_slave_receive()?;
device.enable_slave_notification(RX_NOTIF)?;

let mut msg_buf = [0u8; 256];
loop {
    let msg = sys_recv_open(&mut msg_buf, RX_NOTIF);

    if msg.sender == TaskId::KERNEL && (msg.operation & RX_NOTIF) != 0 {
        match device.get_slave_message() {
            Ok(slave_msg) => {
                // Your protocol logic here
                match parse_message(slave_msg.data()) {
                    Command::Read(reg) => send_register_value(reg),
                    Command::Write(reg, val) => write_register(reg, val),
                    Command::Status => send_status(),
                }
            }
            Err(ResponseCode::NoSlaveMessage) => {}
            Err(_) => {}
        }
    }
}
```

== Error Handling

=== Error Categories

**Configuration Errors:**
- Invalid slave address (reserved, out of range)
- Slave address already in use
- Hardware doesn't support slave mode

**Runtime Errors:**
- Buffer overflow (messages dropped)
- Bus errors during receive
- Hardware malfunction

**Protocol Errors:**
- Invalid message format
- Unexpected message type
- Timeout waiting for continuation

=== Error Recovery

**Handling NoSlaveMessage:**
```rust
match device.get_slave_message() {
    Ok(slave_msg) => {
        // Process message
        process_message(slave_msg.source_address, slave_msg.data());
    }
    Err(ResponseCode::NoSlaveMessage) => {
        // Normal case: notification but message already retrieved
        // or spurious notification
    }
    Err(ResponseCode::SlaveNotEnabled) => {
        // Slave mode was disabled, re-enable if needed
        device.enable_slave_receive()?;
    }
    Err(e) => {
        // Log and handle other errors
        log_error!("Slave receive error: {:?}", e);
    }
}
```

**Configuration Errors:**
```rust
match device.configure_slave_address(0x1D) {
    Ok(()) => {}
    Err(ResponseCode::BadSlaveAddress) => {
        // Address is reserved (0x00-0x07, 0x78-0x7F) or > 0x7F
        log_error!("Invalid slave address");
    }
    Err(ResponseCode::SlaveAddressInUse) => {
        // Another task already configured this address
        log_error!("Slave address already in use");
    }
    Err(ResponseCode::SlaveNotSupported) => {
        // This controller doesn't support slave mode
        log_error!("Slave mode not supported");
    }
    Err(e) => {
        log_error!("Configuration failed: {:?}", e);
    }
}
```

**Reconfiguration After Error:**
```rust
// If communication becomes unreliable
device.disable_slave_notification()?;
device.disable_slave_receive()?;

// Re-initialize
device.configure_slave_address(addr)?;
device.enable_slave_receive()?;
device.enable_slave_notification(mask)?;
```

| Interrupt to buffer
| < 5µs

| Buffer to notification
| < 1µs
| sys_post() overhead

| Notification to client

**Hardware Limit:**
```
At 400 kHz I2C:
- 32 bytes in ~250µs
- Max rate: 4000 messages/sec (theoretical)
```

```
With 5µs interrupt handler:
- Can handle back-to-back messages
- Limited by IPC processing time
- Typical: 1000-2000 messages/sec

== Limitations

=== MCTP-Based Protocol Stacks (SPDM, PLDM)

For protocols that run **over MCTP** (SPDM, PLDM, vendor-defined), the current design
scales well. The MCTP server multiplexes different protocols via the MCTP message type
field, so the single subscriber pattern at the I2C layer is not a limitation.

See link:mctp-i2c-integration.adoc[MCTP-over-I2C Integration] for detailed architecture
and comparisons with other implementations (Caliptra MCU SW).

=== Non-MCTP Multi-Protocol Scenarios

The current implementation is designed for single-protocol deployments at the I2C layer.
For scenarios requiring **multiple independent I2C protocols** (not over MCTP), limitations apply:

|===
| Limitation | Current State | RoT Requirement

| Notification subscribers
| 1 per driver instance (max 2 controllers per instance due to MPU)
| Per-controller or per-protocol subscribers

| Message buffer
| 1 message per driver instance (overwrites on overflow)
| Queue to handle burst traffic without loss

| Overflow handling
| Silent overwrite
| Error signaling, no silent message loss

| Concurrent I2C protocols
| Single protocol per driver instance
| MCTP + raw PMBus + debug simultaneously (separate I2C buses)
|===

**Workarounds for current limitations:**

1. **Single protocol per driver instance** - Current design works well
2. **Dispatcher task** - One task receives all messages from a driver instance, routes based on content
3. **Separate I2C driver instances** - Deploy multiple `openprot-i2c-server` tasks for different controllers (required for 3+ controllers anyway due to MPU constraints)

**Enhancements needed for full RoT support:**

1. Replace single message buffer with a queue (`heapless::Deque`)
2. Add `ResponseCode::SlaveBufferFull` for overflow signaling

=== Comparison with Caliptra MCU SW

The Caliptra MCU SW project implements a similar MCTP-based architecture on Tock OS.
Both projects share fundamental limitations (single message buffer, silent overflow)
and have concluded that protocol demultiplexing belongs at the MCTP layer.

For detailed comparison, see link:mctp-i2c-integration.adoc#comparison-with-other-implementations[MCTP-I2C: Comparison with Other Implementations].

=== Comparison with OpenTitan

OpenTitan's I2C IP represents a more mature design that addresses many limitations
shared by Hubris and Caliptra. This comparison highlights what a robust I2C target
implementation looks like.

**OpenTitan I2C Target Architecture:**

```
┌─────────────────────────────────────────────────┐
│  Software Driver                                │
│  - Threshold-based interrupt handling           │
│  - Software-controlled ACK/NACK                 │

                 │ Register Access
┌────────────────▼────────────────────────────────┐

│  ├── Target Module (slave mode)                 │

**Key OpenTitan Advantages:**

1. **Dual FIFO Architecture** - Separate ACQ (acquisition) and TX (transmit) FIFOs
   allow buffering multiple messages. The ACQ FIFO is sized to absorb a full
   255-byte SMBus Block-Write without software intervention.

2. **Hardware Clock Stretching** - When the ACQ FIFO approaches full, hardware
   automatically stretches SCL before the ACK bit, giving software time to drain
   the buffer. This prevents data loss entirely under normal operation.

3. **Configurable Thresholds** - Interrupts fire when FIFO depth exceeds a
   configurable threshold, not just when data arrives. This enables proactive
   buffer management before overflow occurs.

4. **Software-Controlled ACK/NACK** - The `TARGET_ACK_CTRL` register allows
   software to examine the pending byte via `ACQ_FIFO_NEXT_DATA` before deciding
   whether to ACK or NACK. This enables protocol-level flow control.

5. **Timeout Protection** - If clock stretching persists beyond a configured
   timeout, hardware automatically NACKs the transaction rather than hanging
   the bus indefinitely.

**Implications for Hubris:**

OpenTitan's approach demonstrates that preventing data loss is achievable with
proper hardware support. The "Enhancements needed for full RoT support" section
above could be extended to include:

- Hardware clock stretching support (requires hardware capability)
- Threshold-based notifications (software can approximate with smaller buffers)
- Software-controlled ACK/NACK (requires I2cHardware trait extension)

However, these features require hardware support that may not be available on
all target platforms (e.g., AST1060). The current Hubris design prioritizes
portability and simplicity, relying on higher-layer protocols (MCTP) to handle
retransmission when messages are lost.

== Conclusion

I2C slave mode support in Hubris provides:

✅ **Low Latency**: µs-scale notification delivery
✅ **Memory Efficient**: Single message buffer minimizes RAM usage (~270 bytes)
✅ **Hardware Agnostic**: Uniform API via `I2cDevice` and `I2cHardware` trait
✅ **Power Efficient**: Interrupt-driven, sleep when idle
✅ **Protocol Neutral**: Support any I2C-based protocol (MCTP, PMBus, etc.)
✅ **Type Safe**: Rust memory safety guarantees with `SlaveMessage` struct

**Architecture Goals Achieved:**
1. Application simplicity (high-level `I2cDevice` API)
2. Hardware flexibility (`I2cHardware` trait abstraction)
3. Performance (interrupt-driven via `sys_post()`)
4. Safety (task isolation, typed errors via `ResponseCode`)
5. Maintainability (clear three-layer design)
